    How a request actually moves

    1. Sync request — Browser/client hits api (FastAPI). It talks straight to postgres for reads/writes, checks redis for a rate-limit counter and anything cached, then returns a response immediately.
    2. Durable multi-step workflow — api starts a workflow on temporal and returns immediately with a document id. The temporal-worker process executes the workflow's steps (activities) — extract → chunk → embed → notify — and Temporal persists progress in postgres after each one, so a crash mid-workflow resumes instead of restarting. Watch it live in Temporal UI. This is the only background-execution path — there's no separate task queue; short jobs are just single-activity workflows.
    3. File storage — Any uploaded/generated document goes to minio, which speaks the S3 API — so the same code works against real S3 in staging/production. Reads/writes typically happen inside a workflow activity, not directly in api.
    4. Rate limiting — Each request to a protected route runs an atomic Redis check (INCR + PEXPIRE in one Lua script) keyed by client IP — see app/core/rate_limit.py. Atomic means it stays correct even with multiple api replicas checking the same counter concurrently. Inspect the keys in RedisInsight.
    5. Metrics — api exposes a /metrics endpoint. prometheus scrapes it on a timer, and grafana queries Prometheus to render dashboards.
